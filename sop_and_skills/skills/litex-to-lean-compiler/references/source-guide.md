# Litex to Lean Compiler

Compile the proof route Litex actually checked. A mathematically true Lean
statement, handwritten target file, or independently discovered Lean proof is
not compiler acceptance evidence.

Apply `golitex-repository-policy` and `litex-pipeline-result-types` alongside
this skill. For source proof work, also apply `litex-proof-writer`. For kernel
repairs, apply `litex-kernel-engineer`. A compiler request does not authorize
changing Stmt/Obj/Fact AST structs or Env/ExecEnv/Runtime ownership and storage
contracts; obtain concrete authorization before such changes.

## Artifact ownership

The maintained public Lean tree has exactly this shape:

```text
lean/
  Litex.lean
  examples/
    <math_problem>/
      <stem>.lit
      <stem>.lean
```

- `lean/Litex.lean` owns the complete Lean semantic interface and its proved
  bridge laws. Do not split it into a `lean/Litex/` module tree.
- Each source's first comment explains the mathematical problem. Select a
  real source problem and a descriptive folder/stem, rather than a detached
  compiler-internal demonstration.
- A paired `.lean` is generated by the actual typed-result compiler. Never
  handwrite, patch, or replace it with an expected-output template. Change
  source, compiler, or semantic bridge, then regenerate the pair.
- Keep checks, negative fixtures, receipts, journals, docs, Lake configuration,
  dependencies, build outputs, probes, native adapters and native Final
  consumers under the local-only `scripts/litex_to_lean/` workspace. Do not
  create any of them inside `lean/` or present them as canonical pairs.
- `scripts/legacy_to_lean/` is the ignored historical archive. Preserve it;
  do not import its modules, old generated output, or old build artifacts as
  current evidence. The entire repository-root `scripts/` remains ignored and
  must never be staged, committed, pushed, or published through the parent repo.

This is the user's compiler-specific layout. Follow it over older skill or
repository workflow advice that places compiler drafts or build files elsewhere.

## Anchor the current compiler

The compiler implementation belongs in `src/compile_to_lean/`; its public
entrypoint is `litex -lean -f <source.lit>`. Treat these as the required contract,
not a claim that an implementation or flag is already available.

Before editing, inspect the live AST, execution, verification, storage/inference
results, current compiler module, and `lean/Litex.lean`. Use `rg --files` to
locate renamed owners. Do not copy the obsolete ABI or rely on archived paths.
Choose one source pair as the tracer and state the exact selected proof route,
supported input boundary, expected output, and acceptance commands.

The approved compiler owns only `Runtime`, moved into it after verification
without cloning. It has no lifetime parameter or stored result;
`compile_run(&self, result: &RunLitexCodeResult, namespace)` takes each run as
a method input. Runtime is read-only during compilation. Dispatch existing
result enums in executor-aligned files; leaf
methods return temporary Lean expressions. Derive parameter signatures from
the declaration's original source prefix and spell names from source IDs.
Use a borrowed ancestor/stage cursor for visibility, without persistent object,
numeric, fact, theorem, context, universe or scope registries. A complete run
still needs the live Runtime for missing citation payloads; do not claim that
an isolated result is already a standalone compilation closure.

## Preserve source meaning and WD

Every object retains the carrier-indexed contract:

```text
Obj α = { val : α, wd : WD val }
```

`WD` is proof evidence, not object identity. The registered representation fixes
the denotation independently of which WD proof is supplied. Membership is an
ordinary source fact; it adds knowledge and never retypes a value. Preserve
generic carrier `α` and its representation contract for generic parameters.
Do not choose a numeric host type merely because a later fact proves membership
in R/C or because the variable appears in arithmetic.

Native numeric leaves may retain native ℂ payloads. Non-numeric objects and
operation expressions keep their own Litex representations and construction
shape; do not replace source function objects with native Lean arrows by
convenience. Domain/membership/guard proofs certify a construction or call;
they do not become extra mathematical arguments or select its meaning.

Preserve the source premise that every well-defined object is a set, including
numbers and functions. This does not imply `IsSet → WD`, a default representation
for arbitrary Lean types, or a source set of all objects. Bound set formers and
function domains retain their checked restrictions. Each constructor consumes
the exact child WD and domain proofs returned by its verifier.

Use reviewed denotation/representation laws to connect to native Mathlib values
and theorems. Native equality may lift to semantic equality; elimination back
to native equality needs a proved faithful representation. Do not introduce a
global semantic-equality-to-Lean-Eq shortcut, unsafe cast, project axiom, or proof
hole. If lean/Litex.lean requires an explicit model or representation parameter,
keep it visible and report that condition; do not silently install a candidate
model as the production interpretation.

### Explicit interpretation and native numeric observations

Preserve the accepted meaning of `M : Litex.Semantics`: it is the proof-bearing
dictionary for the common `M.Value`, membership, sethood, numeric embedding,
standard sets and operations. Generated theorems quantify over interpretations
satisfying those laws; native consumers explicitly instantiate a reviewed
model. `Representation M α` fixes a host representation's denotation and WD.
Do not confuse this semantic parameter with the source object's host type.

`In a C` supplies a unique native `ℂ` representative through the existing
`NativeBridge.asComplex`; `asComplex_spec`, `asComplex_proofIndependent` and
`same_iff_asComplex` prove its meaning, proof independence and equality bridge.
These APIs work for every `M : Semantics`, not only NumericModel. Use the
corresponding real APIs for real members. Observations are noncomputable and
preserve the original generic object; they do not retype it or imply equality
of arbitrary host payloads. Replay the original visible membership evidence
when obtaining an observation. Owned operations and functions remain Litex
objects, and numeric observations never authorize a replacement proof route.

For the explanation and current source/generated examples, read
`docs/Litex_To_Lean_Compiler_Guide.md` in the target repository, especially
“Membership preserves the object's representation”.

## Replay typed results

Consume successful `ExecStmtResult`, `VerifyFactResult`, winning `searched_proof`,
WD evidence, and `StoreFactAndInferResult` in their recorded order. Retain original
source subjects, declaration identities and source locations where needed;
rendered strings and saved presentation JSON are not replay input.

- Preserve statement/sibling order, binder identities, assumptions, selected
  rules, ordered child proofs, stores, inference and local scope ownership.
- Emit source producers and hypotheses with their exact FactId names; resolve
  citations from the original visible prefix and ancestors, not a new registry.
  Replay conclusion/component projections and equality-argument matching,
  including substitution, repeated-parameter equalities and orientations.
- Use `result.local_env` and captured parent/module context only to resolve
  exact cited IDs and their subjects. Never scrape an environment to discover
  a new proof, hoist local facts, or rebuild the route by proposition matching.
- Replay constructor WD before truth proofs. Resolve cached WD IDs to the
  previously established WD evidence in the correct scope. If registration,
  assumption, inference or citation provenance is missing, expose that producer
  gap; do not manufacture a proof or infer an owner from rendered text.
- For the standalone MVP, the compiler owns the completed Runtime and uses
  it as a read-only exact-ID resolver. Capture an owned source/citation closure when replay
  must survive Runtime disposal. Neither route permits Runtime proof search;
  this is consumer input, not a second proof log or parallel mutable store.

### Repair missing result evidence

The user has given standing authorization for simple, localized changes to the
result-producing process when statement/verification results omit evidence the
Litex-to-Lean compiler needs. Repair the original producer and its typed return
values rather than adding compiler-owned bookkeeping or reconstructing an
unrecorded proof from the final environment.

Proceed without another confirmation for bounded result-capture changes: retain
already computed parameter introductions, assumptions, WD, selected proof,
store/infer outputs, subjects or exact IDs in the owning result, and propagate
the necessary local signatures and consumers. This includes producer method
bodies on `Runtime` when its state, ownership and execution contracts stay
unchanged. Follow `litex-pipeline-result-types`: preserve actual stage order and
scope ownership; capture existing execution rather than adding proof search,
new facts or a parallel proof log. Verify the affected producer and compiler
consumer, and report the change.

If supplying the missing evidence requires a broad framework refactor, a widely
invasive migration, or changes to ownership, lifecycle, storage/transaction or
search semantics, leave that compiler route unsupported for now or discuss the
concrete design with the user before implementing it. Show the current result,
proposed return shape, affected owners and consequences. Judge locality by the
contracts affected, not just the number of edited lines.

This authorization covers localized result capture; it is not blanket permission
to change protected Stmt/Obj/Fact AST shapes or Env/Runtime owned state and
state-management contracts. Honor any separately granted concrete authorization.

Constructor types may cite local membership/domain proofs. Close exported
propositions over only the required actual producer definitions as ordered
Lean proof-valued `let`s, without new assumptions. A constructor inside a
closed call is not an enclosing WD producer; reject the missing source capture
instead of hoisting it or recovering a replacement from the goal.

Dispatch by the actual successful evidence variant. A target shape may validate
the selected adapter's applicability; it must never choose a replacement proof
route. For example, if `a + 0 = a` was proved by a rational-normalization result,
do not recognize that goal and emit an unrelated add-zero theorem. Support the
recorded normalization certificate with a reviewed adapter or reject it.

Do not launch target theorem search (`aesop`, unrestricted `simp`, etc.). A fixed
normalization tactic is allowed only inside an adapter for an already selected
and validated verifier certificate, with its supported expression domain and
required evidence explicit. Never use Lean to guess the route Litex omitted.

Reject an unsupported statement, object, rule, certificate, reference, carrier
or scope for the whole compilation artifact. Do not silently skip it, emit a
partial theorem file, insert `sorry`, or turn it into an axiom. Source `trust`,
user axioms and named foundation releases need their own explicit reviewed
contracts; `-strict` alone does not establish that every foundation is modeled.

## Three acceptance gates

Keep these gates separate and run them on the exact paired source:

1. **Source:** execute ordinary Litex verification and inspect the actual winning
   result tree. Require exit 0 and the current runner envelope's success flag.
   Check the real CLI schema rather than assuming a historical flag/envelope.
2. **Compiler:** invoke `litex -lean -f lean/examples/<math_problem>/<stem>.lit`.
   Require actual result consumption, complete artifact generation and exit 0.
   Preserve a nearest executable rejected boundary in local tooling when support
   widens; a commented former failure is not that negative gate.
3. **Drift and Lean:** regenerate and compare the paired `.lean` byte for byte,
   then submit the generated file and `lean/Litex.lean` to the pinned real
   Lean/Mathlib kernel. Audit public declarations for unexpected axioms and
   proof holes. Put gate scripts, pinned runtime metadata, output directories
   and receipts under `scripts/litex_to_lean/`; exclude legacy compiled modules
   from import paths.

An optional native Adapter/Final gate belongs in local tooling. Its native
theorem statement must expose ordinary Lean/Mathlib concepts, while its proof
consumes generated output through proved bridges. Disclose model assumptions
and handwritten adapter work; neither substitutes for the three compiler gates.

Report what the source verified, which evidence was compiled, whether the
canonical generated pair is current, and what the real Lean check established.
Separate parser/verifier, result-contract, compiler/ABI and native-adapter gaps.
Never describe a handwritten example or conditional interface check as automatic
compilation or a complete Litex model.
